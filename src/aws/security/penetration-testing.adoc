= AWS: Rules governing penetration testing

Penetration testing is the practice of testing your application's security by
simulating an attack, with the aim of identifying vulnerabilities that could be
exploited in a real attack. Pen testing is typically undertaken by security
experts.

AWS has a customer support policy for penetration testing which, in summary,
says that customers are allowed to carry out pen tests on their own AWS
resources, without prior approval, for a specific set of permitted services,
which include:

* EC2, WAF, NAT gateways, and ELB
* RDS
* CloudFront
* Aurora
* API Gateways
* AppSync
* Lambda and Lambda Edge functions
* Lightsail resources
* Elastic Beanstalk environments
* Elastic Container Service
* Fargate
* OpenSearch Service (formerly Elasticsearch Service)
* FSx
* Transit Gateway
* Bedrock AgentCore
* S3-hosted applications (but targeting S3 buckets directly is strictly
  prohibited)

Testing that includes *Command and Control (C2)* activity always requires
AWS's prior approval, regardless of which service is being tested. Outbound
penetration testing is specifically prohibited for API Gateway and Bedrock
AgentCore.

This permitted-services policy only covers testing of your _own_ resources —
you may never assess AWS's own infrastructure or the underlying AWS services
themselves. If you're a reseller of AWS services, you're responsible for your
customers' testing activity too.

You may use whatever tools you like, but you're solely responsible for
ensuring any DoS-capable functionality in those tools is disabled or otherwise
rendered harmless before use.

Prohibited activities include:

* DNS zone walking via Route 53 Hosted Zones.
* DNS hijacking via Route 53
* DNS pharming via Route 53
* Port flooding
* Protocol flooding
* Request flooding (login request flooding, API request flooding)
* S3 bucket takeover and subdomain takeover

In addition, Denial of Service (DoS), Distributed Denial of Service (DDoS),
Simulated DoS, and Simulated DDoS are subject to the DDoS Simulation Testing
policy, and are essentially all prohibited by default.

== Simulated Events

A separate category of testing — Red/Blue/Purple team exercises with covert
simulation or C2 hosting, iPerf testing, simulated phishing campaigns, malware
testing, network stress/load testing, and DDoS simulations — requires
submitting a *Simulated Events form* to AWS at least *2 weeks* in advance. AWS
aims to respond within *2 business days*.

If a penetration test uncovers a vulnerability in an AWS tool or service
itself (as opposed to your own application), you must report it to AWS
Security within *24 hours* of completing the test.

https://aws.amazon.com/security/penetration-testing/
