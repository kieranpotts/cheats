= VRAM tuning

OOM (out-of-memory) is a common error pattern when running models locally.
This is when the server fails to allocate enough VRAM for the model,
its context, or its compute buffers, and the load or request fails. Ollama
surfaces this as an allocation error naming the failed buffer, eg.
`graph_reserve` or "failed to allocate compute pp buffers".

Four server-level environment variables reduce GPU memory pressure. They are
set once, on the Ollama server, and apply to every model loaded by that
server instance — not per-request.

== `OLLAMA_CONTEXT_LENGTH`

Default context window, in tokens, for every model the server loads. Since
Ollama 0.15.5 the default is no longer a flat `4096` — the server sizes it
from the VRAM it detects at startup.

[cols="1,1"]
|===
|VRAM |Default `num_ctx`

|< 24 GiB
|4,096

|24–48 GiB
|32,768

|>= 48 GiB
|262,144
|===

The KV cache and compute buffers both scale with context length. This is
usually the single largest lever on memory use after the model weights
themselves. An OOM on `graph_reserve` or "failed to allocate compute pp
buffers" is almost always context-related.

Caveats:

* Because the default is VRAM-derived, the same configuration behaves
  differently on different machines — and setting this variable is a real
  change, not a no-op, on any card at 24 GiB or above. On a 32 GiB card the
  server would otherwise pick 32,768.

* This env var only sets the default. A client that sends `options.num_ctx`
  in its API request overrides it for that request, and a model whose own
  Modelfile bakes in `PARAMETER num_ctx` overrides it for that model — some
  published models do exactly this. Check what a given model actually pins
  with `/show parameters` in the REPL (`ollama run`).

* Memory scales as `OLLAMA_NUM_PARALLEL × OLLAMA_CONTEXT_LENGTH`. With
  parallelism above 1, the effective context is a multiple of this number.

Verify with `ollama ps` — the CONTEXT column shows what was actually
allocated.

=== Silent truncation

When a request carries more history than `num_ctx`, Ollama does not error. It
discards the oldest tokens, first-in-first-out, and proceeds — so the model
quietly forgets earlier context. Since the trim takes from the *front*, the
system prompt is typically the first casualty.

WARNING: A front-end's declared context window MUST therefore be less than or
equal to the server's real `num_ctx`. If a harness advertises 128K against a
server allocating 8K, it will keep sending history that is silently thrown
away.

The truncation is logged only at debug level (`server/prompt.go`), so it does
not appear in normal server output. In the runner's journal it shows up
indirectly as `memory_seq_rm` entries.

== `OLLAMA_FLASH_ATTENTION`

Forces flash attention on (`1`) or off (`0`). Default is automatic — Ollama
enables it on its own when the back-end and device support it.

Flash attention reduces memory usage as context size grows, and — more
importantly here — K/V cache quantization only takes effect when flash
attention is enabled, so this is a prerequisite for `OLLAMA_KV_CACHE_TYPE`
below.

Caveat: since selection is already automatic, forcing `1` only changes
anything where Ollama declined to enable it — which on ROCm may mean the
back-end doesn't support it for your GPU/model combination. If it isn't
genuinely active, the KV cache setting won't help either. Check the server
log at startup.

== `OLLAMA_KV_CACHE_TYPE`

Quantization type for the K/V context cache. Default is `f16`.

[cols="1,1,3"]
|===
|Value |Memory vs `f16` |Quality impact

|`f16`
|baseline
|None. Default, highest precision.

|`q8_0`
|~1/2
|Very small precision loss, usually no noticeable quality impact. The
recommended choice if not using `f16`.

|`q4_0`
|~1/4
|Small-to-medium precision loss, more noticeable at higher context sizes.
|===

Roughly halves the KV cache allocation at `q8_0`. The larger the context, the
more this saves in absolute terms.

Caveats:

* Global option — every model on the server runs with this quantization
  type. There is no per-model override.

* Requires flash attention (see above).

* Quality impact is model-dependent. Models with a high GQA count (eg.
  Qwen2) may lose more precision from quantization than low-GQA models.
  Worth A/B-ing on your actual workload if output quality matters.

== `OLLAMA_MAX_LOADED_MODELS`

Caps how many models may be resident in memory simultaneously. Default is
`3 × number of GPUs` (or `3` for CPU inference).

With the default of 3, a second or third model loaded by some other client
can quietly consume the headroom your primary model needs, producing an OOM
that looks unrelated to what you were doing. Setting it to `1` guarantees one
model owns the GPU at a time. Others queue rather than compete.

Caveats:

* Trade-off is latency. Switching between models now forces an
  unload/reload cycle.

* On Windows with Radeon GPUs this is already the effective default (ROCm
  v5.7 VRAM reporting limitations), so setting it there is redundant —
  harmless, but it isn't what fixed the problem.

* Doesn't cap parallel requests to a single model — that's
  `OLLAMA_NUM_PARALLEL`, which multiplies context memory and is worth
  pinning to `1` alongside this if VRAM is tight.

* Related: `OLLAMA_KEEP_ALIVE` (default `5m`) controls how long an idle
  model holds its VRAM. Shortening it frees memory sooner between uses.

== Applying the configuration

IMPORTANT: The `ollama` systemd service does not inherit your shell
environment. Exporting these variables in `.bashrc` or `.profile` has no
effect on the running server — they must be set on the service itself.

On Linux, set these as a systemd drop-in on `ollama.service`:

[source,sh]
----
sudo systemctl edit ollama.service
----

[source,ini]
----
[Service]
# Default context window for all models, in tokens. KV cache and compute
# buffers scale with this — the main lever on VRAM use.
Environment="OLLAMA_CONTEXT_LENGTH=4096"

# Force Flash Attention on. Reduces memory at longer contexts, and is a
# prerequisite for K/V cache quantization below.
Environment="OLLAMA_FLASH_ATTENTION=1"

# Quantize the K/V cache to 8-bit: ~half the memory of f16, negligible
# quality cost. Global — applies to every model on this server.
Environment="OLLAMA_KV_CACHE_TYPE=q8_0"

# One model resident at a time (default is 3 per GPU). Stops a second
# model from eating the headroom the first one needs.
Environment="OLLAMA_MAX_LOADED_MODELS=1"
----

[source,sh]
----
sudo systemctl daemon-reload
sudo systemctl restart ollama
----

Other platforms:

* macOS: `launchctl setenv NAME value`, then restart the app.

* Windows: set the variables via the Settings/Control Panel environment
  variables dialogue (Ollama inherits user/system environment variables),
  then quit and relaunch Ollama.

== Verifying it took effect

[source,sh]
----
ollama ps                       # CONTEXT column = actual allocated context.
                                # PROCESSOR column = GPU/CPU split.
rocm-smi                        # Actual VRAM in use, and by what.
journalctl -u ollama -f         # Startup log: back-end, flash attention, buffer sizes.
----

In the REPL, `/show parameters` reveals whether a model pins its own
`num_ctx`, overriding the server default.

== Not covered by these variables

`num_batch` (prompt-processing batch size, default `512`) and `num_gpu`
(layers offloaded to GPU) have no server-wide environment variable. They are
set per-request via the API `options` object, or baked into a model with a
link:./modelfiles.adoc[Modelfile]:

[source]
----
FROM your-model:tag
PARAMETER num_ctx 4096
PARAMETER num_batch 256
PARAMETER num_gpu 20
----

[source,sh]
----
ollama create your-model:4k -f Modelfile
----
